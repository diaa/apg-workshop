4. Deploy with Bicep

Learning Objectives
  • Log in to Azure and set the correct subscription
  • Deploy Azure PostgreSQL Flexible Server via Bicep (Enterprise or Simple path)
  • Understand the deployed architecture (VNet, subnets, jumpbox, DNS)
  • Verify connectivity by SSH-ing to the jumpbox and running psql
⏱ Timing: 20–30 minutes (login + deploy ~15 min + SSH verification)

Prerequisites Check

Before starting, verify each attendee has:

  • Azure CLI installed (az --version)
  • An Azure subscription with Contributor access (az account show)
  • The workshop templates (zip extraction or git clone)

Option 1 — Enterprise Deployment (Recommended)

Deploys the full hub-and-spoke architecture: jumpbox VM, private VNet, PostgreSQL Flexible Server with private access, and private DNS zone.

Step 1 — Extract templates and navigate

# If using the zip file:
cd C:\path\to\extracted\bicep

# Or clone the repo:
git clone https://github.com/Azure/apg-workshop.git
cd apg-workshop/bicep

Step 2 — Log in to Azure

az login

Opens a browser window for authentication. If multiple subscriptions, set the correct one:

az account set --subscription "<subscription-name-or-id>"

Step 3 — Create the resource group

az group create --name PG-Workshop --location uksouth

The resource group must exist before deployment. If attendees skip this, deployment fails with "ResourceGroupNotFound".

Step 4 — Deploy the Bicep template

az deployment group create --resource-group PG-Workshop --template-file main.bicep

Attendees will be prompted for four values:

ParameterDescription
vmAdminUsernameUsername for the jumpbox VM (e.g. workshopuser)
vmAdminPasswordStrong password for the jumpbox VM
postgreSqlAdministratorLoginUsername for PostgreSQL — use your name, avoid admin or root
postgreSqlAdministratorLoginPasswordStrong password (min 8 chars, mix of upper/lower/number/special)

Deployment takes 10–15 minutes. The outputs contain the jumpbox public IP and PostgreSQL FQDN.

Step 5 — SSH into the jumpbox and verify

ssh <vmAdminUsername>@<jumpbox-public-ip>

Use the VM password from Step 4. Once connected:

# Verify psql is installed
psql --version

# Test database connectivity
psql -h <postgresql-fqdn> -U <pgAdminUsername> -d postgres

If you see postgres=>, the deployment is working. psql should report version 18.x.

Option 2 — Simple Deployment (Public Network)

Deploys only a PostgreSQL Flexible Server with a public endpoint and a firewall rule. No jumpbox VM — attendees connect directly from their machine.

Step 1 — Navigate to the simple folder

# From extracted zip:
cd C:\path\to\extracted\bicep\simple

# Or from cloned repo:
cd apg-workshop/bicep/simple

Step 2 — Log in and create the resource group

az login
az group create --name PG-Workshop --location uksouth

Step 3 — Get your public IP

# PowerShell (Windows):
(Invoke-WebRequest -Uri "https://ifconfig.me/ip").Content

# Bash (Linux/macOS/Cloud Shell):
curl -s ifconfig.me

Step 4 — Deploy

az deployment group create --resource-group PG-Workshop \
  --template-file main.bicep \
  --parameters clientIPAddress="<your-public-ip>"

Prompted for administratorLogin and administratorPassword (min 12 chars).

Step 5 — Connect from local machine

psql "host=<server-fqdn> user=<administratorLogin> dbname=postgres sslmode=require"

If psql is not installed locally, use the Azure Portal → PostgreSQL server → Connect blade.

Proctor Notes
  • Recommend Option 1 for most workshops — it teaches real-world private networking and gives hands-on SSH experience.
  • Fall back to Option 2 if time is short, attendees have restricted subscriptions, or the audience is developer-focused.
  • az login and subscription selection is the first thing to verify — don't let attendees skip it.
  • If git isn't available: wget https://pg.azure-workshops.cloud/scripts/bicep.zip && unzip bicep.zip
  • During the 10–15 min deployment wait, walk through the architecture diagram or answer conceptual questions about Azure PostgreSQL.
  • For Option 1 Step 5, attendees must use the jumpbox-public-ip from deployment outputs, not the PG server IP.
Common Pitfalls
  • "ResourceGroupNotFound": Attendee skipped az group create. Must create the resource group before deploying.
  • "SubscriptionNotFound" / wrong subscription: Run az account set --subscription <id>.
  • Deployment fails with "InternalServerError": PG v18 may not be available in the selected region. Use uksouth.
  • Password rejected: Enterprise: min 8 chars. Simple: min 12 chars. Both need upper/lower/number/special.
  • SSH "Connection refused": Check the jumpbox NSG allows port 22 from the attendee's IP.
  • Option 2 "connection timed out": The firewall IP doesn't match the attendee's actual public IP (VPN/proxy). Re-run the IP check and update the firewall in the Portal.

5. Connecting to PostgreSQL

Learning Objectives
  • SSH into the jumpbox VM
  • Connect to PostgreSQL using psql
  • Understand private DNS resolution within VNet
⏱ Timing: 10–15 minutes

Key Commands

SSH into the jumpbox

ssh <admin-user>@<jumpbox-public-ip>

The jumpbox is in the hub VNet and can reach the PG server via private DNS.

Set environment variables for convenience

export PGHOST=<postgresql-fqdn>
export PGUSER=<pgadmin>
export PGDATABASE=postgres
export PGSSLMODE=require

Avoids typing host/user on every psql command. PGHOST is the private DNS name of the server.

Connect with psql

psql

With env vars set, a bare psql connects automatically. Prompt should show postgres=>.

Proctor Notes
  • The jumpbox public IP is in the deployment outputs tab in the Portal.
  • For Simple deployments, attendees connect directly from Cloud Shell or their laptop (public endpoint).
  • Suggest attendees save env vars in ~/.pg_azure and source it — the workshop provides a helper script.
Common Pitfalls
  • "Connection refused" / timeout: NSG may be blocking SSH. Check the jumpbox NSG allows port 22 from the attendee's IP.
  • "could not translate host name": Private DNS zone isn't linked to the hub VNet. Check the DNS zone virtual network links in the Portal.
  • SSL errors: Ensure PGSSLMODE=require is set.

6. Connection Methods & Troubleshooting

Learning Objectives
  • Understand multiple connection methods (psql, pgAdmin, Azure Data Studio, VS Code)
  • Use .pgpass for password-less connections
  • SSH tunnel as a fallback for private endpoints
  • Troubleshoot common connection failures
⏱ Timing: 10 minutes

Key Commands

Create a .pgpass file (password-less auth)

echo "<pg-fqdn>:5432:*:<admin>:<password>" > ~/.pgpass
chmod 600 ~/.pgpass

.pgpass stores credentials securely. chmod 600 is required — psql refuses to read the file otherwise.

SSH tunnel (for GUI tools on laptop)

ssh -L 5432:<pg-private-ip>:5432 <admin>@<jumpbox-ip>

Forwards local port 5432 through the jumpbox to the private PG endpoint. GUI tools connect to localhost:5432.

Proctor Notes
  • Most attendees will use psql on the jumpbox. GUI tools are nice-to-have, not required.
  • If anyone is stuck with .pgpass, check that the hostname in .pgpass matches $PGHOST exactly.
  • The file covers pgAdmin 4, Azure Data Studio, and VS Code PostgreSQL extension — all optional.
Common Pitfalls
  • .pgpass ignored: Permissions must be 600. Run chmod 600 ~/.pgpass.
  • SSH tunnel drops: Add -o ServerAliveInterval=60 to the SSH command.
  • DNS mismatch in .pgpass: Use the same FQDN as $PGHOST.

8. Load Data (orders_demo)

Learning Objectives
  • Create and restore the orders_demo database from a custom-format dump
  • Understand the database schema (4 tables, ~410K rows)
  • Enable and verify pg_stat_statements
⏱ Timing: 15–20 minutes

Database Schema

TableRowsPurpose
customers~10,000Customer profiles with loyalty points
products~500Product catalog with categories
orders~100,000Orders with status, shipping country, amounts
order_items~300,000Line items with quantity, price, discount

Key Commands (in order)

Step 1 — SSH to jumpbox

ssh <admin-user>@<jumpbox-ip>
source ~/.pg_azure

Step 2 — Connect and create database

psql
CREATE DATABASE orders_demo;

Step 3 — Download and restore the dump

cd /tmp
curl -O https://pg.azure-workshops.cloud/database/workshop_backup.dump
pg_restore -h $PGHOST -U $PGUSER -d orders_demo --no-owner --verbose /tmp/workshop_backup.dump

Downloads the pre-built dump file from the workshop CDN and restores it with pg_restore. The --no-owner flag avoids errors about missing original roles.

Step 4 — Verify the data

psql -d orders_demo

SELECT 'customers' AS tbl, COUNT(*) FROM customers
UNION ALL SELECT 'products', COUNT(*) FROM products
UNION ALL SELECT 'orders', COUNT(*) FROM orders
UNION ALL SELECT 'order_items', COUNT(*) FROM order_items;

Should show ~10K, ~500, ~100K, ~300K rows respectively.

Step 5 — Enable pg_stat_statements

CREATE EXTENSION IF NOT EXISTS pg_stat_statements;
SELECT calls, total_exec_time, mean_exec_time, LEFT(query, 60)
FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 5;

Must be enabled BEFORE running the workload — it captures query statistics from this point forward.

Proctor Notes
  • This is a critical checkpoint. Every attendee must finish this section before proceeding. All subsequent labs depend on orders_demo.
  • If curl fails: check if the jumpbox has internet access. For VNet-injected servers, the outbound route may be missing. Help configure NAT gateway or use the Portal to download.
  • If pg_stat_statements fails with "must be loaded via shared_preload_libraries": go to Portal → Server parameters → search shared_preload_libraries → check pg_stat_statements → Save (requires restart).
Common Pitfalls
  • pg_restore errors about "role does not exist": Safe to ignore — --no-owner handles ownership, but warnings about the original dump owner still appear.
  • Database already exists: DROP DATABASE orders_demo; and recreate. Check nobody else is connected first.
  • Dump URL doesn't work: Verify internet access from jumpbox with curl -I https://pg.azure-workshops.cloud.

9. Run Demo Workload

Learning Objectives
  • Generate intentionally heavy CPU, IOPS, and temp file load
  • Understand why these queries are expensive (cross-joins, correlated subqueries, window functions, md5 loops)
  • Practice observing active queries via pg_stat_activity
  • Create baseline metrics for later monitoring and tuning labs
⏱ Timing: 20–30 minutes (queries themselves take time; use waiting periods for discussion)

The 6 Heavy Queries

Attendees open multiple psql sessions (at least 2–3 terminals) and run queries concurrently to generate load.

Query 1 — Cross-Join Aggregation (CPU + IOPS heavy)

SELECT c.city, c.country, p.category,
       COUNT(DISTINCT o.order_id) AS total_orders,
       SUM(oi.quantity * oi.unit_price * (1 - oi.discount/100)) AS revenue
FROM customers c
JOIN orders o ON o.customer_id = c.customer_id
JOIN order_items oi ON oi.order_id = o.order_id
JOIN products p ON p.product_id = oi.product_id
GROUP BY c.city, c.country, p.category
ORDER BY revenue DESC;

Why it's expensive: 4-table join with GROUP BY on high-cardinality columns. Produces large intermediate hash tables. No indexes help yet.

Query 2 — Correlated Subquery (N+1 anti-pattern)

SELECT c.customer_id, c.first_name, c.last_name,
       (SELECT COUNT(*) FROM orders o WHERE o.customer_id = c.customer_id) AS order_count,
       (SELECT COALESCE(SUM(total_amount),0) FROM orders o WHERE o.customer_id = c.customer_id) AS lifetime_value
FROM customers c
ORDER BY lifetime_value DESC
LIMIT 100;

Why it's expensive: Two correlated subqueries execute once per customer row (10K × 2 = 20K sub-plans). This is the classic "N+1" problem solvable by indexing.

Query 3 — Window Functions (memory + sort heavy)

SELECT order_id, customer_id, order_date, total_amount,
       SUM(total_amount) OVER (PARTITION BY customer_id ORDER BY order_date) AS running_total,
       ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY total_amount DESC) AS rank_by_amount,
       AVG(total_amount) OVER (PARTITION BY shipping_country ORDER BY order_date
            ROWS BETWEEN 100 PRECEDING AND CURRENT ROW) AS moving_avg
FROM orders;

Why it's expensive: Three window functions with different PARTITION BY clauses require multiple full sorts of 100K rows. Generates temp files when work_mem is low.

Query 4 — Heavy Text Computation + Sort

SELECT c.email, md5(c.email || o.order_id::TEXT) AS hash_key,
       string_agg(p.product_name, ', ' ORDER BY oi.unit_price DESC) AS products_bought
FROM customers c
JOIN orders o ON o.customer_id = c.customer_id
JOIN order_items oi ON oi.order_id = o.order_id
JOIN products p ON p.product_id = oi.product_id
GROUP BY c.email, o.order_id
ORDER BY hash_key;

Why it's expensive: MD5 computation on every row, string aggregation, and final sort on computed hash key. Pure CPU burn.

Query 5 — Repeated Sequential Scan Loop

DO $$
BEGIN
  FOR i IN 1..20 LOOP
    PERFORM COUNT(*) FROM orders o
    JOIN order_items oi ON oi.order_id = o.order_id
    WHERE md5(o.status || oi.quantity::TEXT) LIKE '00%';
  END LOOP;
END $$;

Why it's expensive: The md5() filter is not indexable — forces full sequential scan every iteration. 20 loops × full table scan. Increase to 50–100 for more load.

Query 6 — Large Temp-Table Sort + Distinct

SELECT DISTINCT ON (customer_id)
       customer_id, order_id, order_date, total_amount
FROM orders
ORDER BY customer_id, total_amount DESC, order_date DESC;

Why it's expensive: Full sort of 100K rows on a composite key. Without a matching index, PG writes temp files. Solvable with a composite index in the index tuning lab.

Diagnostic Queries (run from a separate session)

Active queries

SELECT pid, state, query_start, LEFT(query, 80) AS query_snippet
FROM pg_stat_activity
WHERE datname = 'orders_demo' AND state != 'idle'
ORDER BY query_start;

Sequential scan stats

SELECT relname AS table, seq_scan, seq_tup_read, idx_scan, idx_tup_fetch
FROM pg_stat_user_tables ORDER BY seq_tup_read DESC;

Temp file usage

SELECT datname, temp_files, pg_size_pretty(temp_bytes) AS temp_size
FROM pg_stat_database WHERE datname = 'orders_demo';
Proctor Notes
  • This section is critical for Day 2. The monitoring and index tuning labs depend on query stats generated here.
  • Have attendees enable \timing before running queries so they capture baseline timings.
  • Encourage them to write down the execution times — they'll compare before/after in the index tuning lab.
  • Walk around and ensure at least 2–3 queries are running concurrently across sessions.
  • If attendees finish quickly, have them increase Query 5's loop count to 50 or 100.
  • The diagnostic queries are a great teaching moment — explain pg_stat_activity and pg_stat_user_tables.

10. Managing PostgreSQL DB

Learning Objectives
  • Scale compute & storage via Portal
  • Modify server parameters at different levels (server, database, role, session)
  • Enable built-in PgBouncer
  • Add resource locks for delete protection
⏱ Timing: 15–20 minutes

Portal Actions

  1. Navigate to Compute + Storage blade → observe SKU options (Burstable, General Purpose, Memory Optimized)
  2. Navigate to Server parameters → search and modify a parameter (e.g., work_mem)
  3. Search pgbouncer → set to TRUE → Save
  4. Navigate to Locks → +Add → Lock name: DoNotDelete → Type: Delete

Verify PgBouncer

psql -p 6432
SHOW pgbouncer;

Port 6432 is the PgBouncer port. SHOW pgbouncer returns the current status.

Proctor Notes
  • Emphasize that parameter changes have different contexts: user (session SET), sighup (no restart), postmaster (requires restart).
  • After enabling PgBouncer, the server restarts. Warn attendees it takes 1–2 minutes.
  • Resource locks are a quick but powerful governance feature — good talking point for ops teams.

11. Roles & Permissions

Learning Objectives
  • PostgreSQL role model — no "users" or "groups", only roles
  • INHERIT vs NOINHERIT behavior
  • GRANT and REVOKE privileges
  • DEFAULT PRIVILEGES for future objects
  • Schema isolation
  • Azure-specific roles (azure_pg_admin, azuresu)
⏱ Timing: 25–35 minutes (lots of SQL; take it step by step)

Role Setup

CREATE ROLE app_team NOLOGIN;
CREATE ROLE readonly NOLOGIN;
CREATE ROLE dev_user LOGIN PASSWORD 'Workshop#Dev1' IN ROLE app_team INHERIT;
CREATE ROLE analyst_user LOGIN PASSWORD 'Workshop#Read1' IN ROLE readonly INHERIT;
CREATE ROLE contractor_user LOGIN PASSWORD 'Workshop#Ext1' IN ROLE app_team NOINHERIT CONNECTION LIMIT 2;

Creates a role hierarchy: app_team (read/write), readonly (read-only). dev_user inherits from app_team. contractor_user does NOT inherit — must explicitly SET ROLE.

Grant Privileges

GRANT USAGE ON SCHEMA public TO app_team;
GRANT ALL ON ALL TABLES IN SCHEMA public TO app_team;
GRANT ALL ON ALL SEQUENCES IN SCHEMA public TO app_team;
GRANT USAGE ON SCHEMA public TO readonly;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO readonly;

-- Required for SET ROLE to work:
GRANT dev_user TO <your-admin>;
GRANT analyst_user TO <your-admin>;
GRANT contractor_user TO <your-admin>;

Test INHERIT vs NOINHERIT

dev_user (INHERIT) — should succeed

SET ROLE dev_user;
SELECT customer_id, first_name, last_name, email FROM customers LIMIT 5;
INSERT INTO customers (first_name, last_name, email, city, country)
VALUES ('Test', 'User', 'test@workshop.dev', 'London', 'United Kingdom');
RESET ROLE;

dev_user inherits app_team's privileges → SELECT and INSERT both work.

analyst_user (readonly) — INSERT should fail

SET ROLE analyst_user;
SELECT status, COUNT(*) FROM orders GROUP BY status;          -- ✅ works
INSERT INTO customers (...) VALUES (...);                     -- ❌ ERROR: permission denied
RESET ROLE;

contractor_user (NOINHERIT) — SELECT should fail until SET ROLE

SET ROLE contractor_user;
SELECT * FROM customers LIMIT 1;       -- ❌ ERROR (no inherited privs)
SET ROLE app_team;                      -- Explicitly assume the role
SELECT * FROM customers LIMIT 5;       -- ✅ works
RESET ROLE;

This is the key lesson: NOINHERIT requires an explicit SET ROLE to assume privileges. Useful for contractors/external users.

Cleanup (important!)

-- Must revoke grants, drop schemas, then drop roles in order
REVOKE ALL ON ALL TABLES IN SCHEMA public FROM app_team;
REVOKE ALL ON ALL TABLES IN SCHEMA public FROM readonly;
REVOKE ALL ON ALL SEQUENCES IN SCHEMA public FROM app_team;
REVOKE USAGE ON SCHEMA public FROM app_team;
REVOKE USAGE ON SCHEMA public FROM readonly;
GRANT CREATE ON SCHEMA public TO PUBLIC;
ALTER DEFAULT PRIVILEGES IN SCHEMA public REVOKE SELECT ON TABLES FROM readonly;
ALTER DEFAULT PRIVILEGES IN SCHEMA public REVOKE ALL ON TABLES FROM app_team;
GRANT ALL ON ALL TABLES IN SCHEMA public TO <your-admin>;
DROP SCHEMA IF EXISTS app;
DROP ROLE IF EXISTS dev_user;
DROP ROLE IF EXISTS analyst_user;
DROP ROLE IF EXISTS contractor_user;
DROP ROLE IF EXISTS app_team;
DROP ROLE IF EXISTS readonly;
DELETE FROM customers WHERE email IN ('test@workshop.dev', 'another@workshop.dev');
Proctor Notes
  • Cleanup is essential. If roles are left behind, later labs may behave unexpectedly.
  • Common question: "Why can't I drop a role?" → Role still owns objects or has dependencies. Must REVOKE first.
  • Explain the privilege code shorthand: r = SELECT, a = INSERT, w = UPDATE, d = DELETE, D = TRUNCATE.
  • Highlight that azure_pg_admin is the highest role attendees can use — azuresu is reserved by Azure.
Common Pitfalls
  • "permission denied for role": Admin must GRANT the role to themselves before SET ROLE. The workshop includes GRANT dev_user TO <admin>; — don't skip it.
  • Roles not dropped in order: Must revoke privileges → drop dependent roles → drop parent roles.

12. Connection Pooling (PgBouncer) Optional

Learning Objectives
  • Understand the process-per-connection model in PostgreSQL
  • Configure built-in PgBouncer on Azure Flexible Server
  • Compare performance with and without pooling using pgbench
  • Monitor PgBouncer via its virtual database
⏱ Timing: 15–20 minutes (skip if behind schedule)

Portal Configuration

Server parameters → set: pgbouncer.enabled = true, pgbouncer.pool_mode = transaction, pgbouncer.default_pool_size = 20, pgbouncer.max_client_conn = 200, pgbouncer.min_pool_size = 5 → Save (restart required).

pgbench Comparison

# Direct connection (port 5432)
pgbench -h $PGHOST -U $PGUSER -d orders_demo -p 5432 -c 50 -j 4 -T 30 -S

# Through PgBouncer (port 6432)
pgbench -h $PGHOST -U $PGUSER -d orders_demo -p 6432 -c 50 -j 4 -T 30 -S

-c 50 = 50 concurrent clients, -j 4 = 4 threads, -T 30 = 30 seconds run, -S = SELECT-only. Compare TPS between direct and pooled.

Monitor via PgBouncer virtual database

psql -h $PGHOST -U $PGUSER -d pgbouncer -p 6432
SHOW POOLS;
SHOW STATS;
SHOW CLIENTS;
SHOW SERVERS;
Proctor Notes
  • PgBouncer TPS improvement is dramatic — typically 3–10× with 50 connections.
  • Explain pool modes: transaction (recommended), session (legacy), statement (rare, breaks multi-statement transactions).
  • This is a great section for DBAs; devs may find it less engaging. Adjust depth accordingly.

13. Logical Backup & Restore

Learning Objectives
  • Understand three dump formats: plain SQL, custom, directory
  • Use pg_dump with selective options (schema-only, data-only, single table)
  • Restore with pg_restore including parallel restore (-j 4)
  • Use pg_dumpall for global objects
⏱ Timing: 20–25 minutes

Key Commands

Three dump formats

# Plain SQL
pg_dump orders_demo > /tmp/orders_demo.plain.sql

# Custom format (compressed, pg_restore required)
pg_dump -Fc orders_demo -f /tmp/orders_demo.custom.dump

# Directory format (parallel-ready)
pg_dump -Fd -j 4 orders_demo -f /tmp/orders_demo_dir

Selective dumps

pg_dump --schema-only orders_demo > /tmp/orders_demo_ddl.sql
pg_dump --data-only orders_demo > /tmp/orders_demo_data.sql
pg_dump --data-only --inserts orders_demo > /tmp/orders_demo_inserts.sql
pg_dump --table=customers orders_demo > /tmp/customers.sql

Restore

psql -d postgres -c "CREATE DATABASE orders_demo_restored;"
pg_restore -d orders_demo_restored --no-owner --verbose /tmp/orders_demo.custom.dump

# Verify
psql -d orders_demo_restored -c "SELECT 'customers' AS tbl, COUNT(*) FROM customers

21. MVCC Deep Dive

Learning Objectives
  • Understand MVCC mechanism — xmin/xmax system columns
  • UPDATE creates a new row version; DELETE marks rows dead
  • VACUUM reclaims dead tuple space (doesn't shrink file)
  • VACUUM FULL rewrites the table (shrinks file, needs exclusive lock)
  • Autovacuum thresholds and per-table tuning
⏱ Timing: 25–35 minutes

Key Flow

  1. Check baseline: n_live_tup, n_dead_tup, table size
  2. Observe MVCC columns: SELECT ctid, xmin, xmax FROM customers LIMIT 5
  3. Generate dead tuples: UPDATE customers SET loyalty_points = loyalty_points + 10 (×2)
  4. Check dead tuples increased, table size grew
  5. Run VACUUM VERBOSE customers — dead tuples reclaimed, but table size unchanged
  6. Run VACUUM FULL VERBOSE customers — table rewritten, size shrinks
  7. DELETE rows and repeat the cycle with orders/order_items
  8. Explore autovacuum settings: SHOW autovacuum_vacuum_scale_factor
  9. Set per-table threshold: ALTER TABLE orders SET (autovacuum_vacuum_scale_factor = 0.05)

Key SQL Queries

Observe MVCC columns

SELECT ctid, xmin, xmax, customer_id, first_name
FROM customers LIMIT 5;

ctid = physical row location (page, offset). xmin = transaction that created this version. xmax = transaction that deleted/updated it (0 = still live).

Generate dead tuples

UPDATE customers SET loyalty_points = loyalty_points + 10;
UPDATE customers SET loyalty_points = loyalty_points + 10;

SELECT relname, pg_size_pretty(pg_relation_size(relid)) AS table_size,
       n_live_tup, n_dead_tup
FROM pg_stat_user_tables WHERE relname = 'customers';

After two UPDATEs, there are ~20K dead tuples (10K per UPDATE). Table size has grown.

VACUUM vs VACUUM FULL

VACUUM VERBOSE customers;    -- Reclaims dead space for reuse, but file size stays same
VACUUM FULL VERBOSE customers;  -- Rewrites entire table, file shrinks

Autovacuum tuning

SHOW autovacuum_vacuum_threshold;       -- default 50
SHOW autovacuum_vacuum_scale_factor;    -- default 0.20 (20%)
-- Formula: vacuum triggers when dead_tuples > threshold + scale_factor × n_live_tup

ALTER TABLE orders SET (autovacuum_vacuum_scale_factor = 0.05);  -- 5% for high-traffic tables
Proctor Notes
  • This is conceptually challenging for attendees from Oracle/SQL Server backgrounds. In Oracle, dead data goes to the undo tablespace. In SQL Server, tempdb. In PostgreSQL, dead tuples stay in the table until VACUUM.
  • Key insight: VACUUM is like clearing recycle bin (space is reusable but file doesn't shrink). VACUUM FULL is like defragmenting (rewrites file, needs exclusive lock).
  • Warn that VACUUM FULL takes an ACCESS EXCLUSIVE lock — never run it on production during business hours.
  • DELETE of orders/order_items may fail with FK constraint. If so, delete order_items first, then orders.

22. Parameter Tuning

Learning Objectives
  • Understand parameter context levels (user, superuser, sighup, postmaster)
  • Tune work_mem and observe impact on sorts/temp files
  • Tune maintenance_work_mem and observe index creation speed
  • Tune random_page_cost and observe planner behavior change
  • Sizing guidelines for each parameter
⏱ Timing: 25–35 minutes

work_mem Lab

-- Low work_mem → sort spills to disk
SET work_mem = '4MB';
EXPLAIN (ANALYZE, BUFFERS)
SELECT DISTINCT ON (customer_id) customer_id, order_id, order_date, total_amount
FROM orders ORDER BY customer_id, total_amount DESC, order_date DESC;

-- High work_mem → in-memory sort
SET work_mem = '64MB';
EXPLAIN (ANALYZE, BUFFERS)
SELECT DISTINCT ON (customer_id) customer_id, order_id, order_date, total_amount
FROM orders ORDER BY customer_id, total_amount DESC, order_date DESC;

RESET work_mem;

With 4MB, the EXPLAIN output shows Sort Method: external merge Disk. With 64MB, it shows Sort Method: quicksort Memory. Dramatic timing difference.

maintenance_work_mem Lab

SET maintenance_work_mem = '64MB';
\timing
CREATE INDEX idx_orders_cust_amount_date ON orders (customer_id, total_amount DESC, order_date DESC);
DROP INDEX idx_orders_cust_amount_date;

SET maintenance_work_mem = '512MB';
CREATE INDEX idx_orders_cust_amount_date ON orders (customer_id, total_amount DESC, order_date DESC);
RESET maintenance_work_mem;

More maintenance_work_mem = faster index creation/VACUUM. Time the difference.

random_page_cost Lab

SET random_page_cost = 4.0;    -- default (spinning disk assumption)
EXPLAIN SELECT * FROM orders WHERE customer_id BETWEEN 100 AND 200;

SET random_page_cost = 1.1;    -- SSD-appropriate
EXPLAIN SELECT * FROM orders WHERE customer_id BETWEEN 100 AND 200;
RESET random_page_cost;

With 4.0, the planner may choose Seq Scan (random IO is expensive). With 1.1, it prefers Index Scan (random IO is cheap on SSD). Azure uses SSDs → 1.1 is appropriate.

23. SQL Characteristics (Partial Indexes + JSONB)

Learning Objectives
  • Partial indexes — index only rows matching a WHERE condition
  • JSONB data type — semi-structured data in PostgreSQL
  • JSONB operators: ->, ->>, @>, ?, #>>
  • GIN indexes on JSONB columns
  • jsonb_set, jsonb_each_text
⏱ Timing: 25–30 minutes

Partial Index Lab

CREATE SCHEMA IF NOT EXISTS games;
SET SEARCH_PATH TO games;

CREATE TABLE games (
    id         BIGINT PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY,
    start_time TIMESTAMP NOT NULL DEFAULT now(),
    end_time   TIMESTAMP NOT NULL,
    players    INTEGER[] NOT NULL,
    winner     INTEGER,
    is_activ   BOOLEAN DEFAULT TRUE
);

-- Insert ~15M rows
INSERT INTO games (start_time, end_time, players, winner, is_activ)
SELECT d, d + '1 hour', ('{' || n || ',' || n + 4 || '}')::INT[], n, TRUE
FROM generate_series(1, 10000) n,
     generate_series('2021-01-01'::TIMESTAMP, now()::TIMESTAMP, '1 day'::INTERVAL) d;

-- Mark most games as inactive
UPDATE games SET is_activ = FALSE WHERE start_time::date <> CURRENT_DATE;

-- Run 4–5 times, observe timing
SELECT count(*) FROM games WHERE is_activ;

-- Create partial index
CREATE INDEX ON games(id) WHERE is_activ;

-- Run again — dramatic speedup
SELECT count(*) FROM games WHERE is_activ;

Without the partial index, PG scans millions of rows. With the partial index, it only scans the few thousand active rows. Typically 100×+ improvement.

JSONB Lab

-- Create table with JSONB column
CREATE TABLE products (name TEXT, attributes JSONB);

INSERT INTO products (name, attributes)
VALUES ('Leffe Blonde Ale',
        '{"category": "Golden / Blonde Ale", "region": "Belgium", "ABV": 6.6}');

-- Operators demo
SELECT name, attributes -> 'ABV' FROM products;           -- returns JSON value
SELECT name, attributes ->> 'ABV' FROM products;          -- returns text
SELECT name FROM products WHERE attributes @> '{"region": "Belgium"}';  -- containment

-- GIN index
CREATE INDEX ON products USING gin(attributes);
EXPLAIN SELECT name FROM products WHERE attributes @> '{"region": "Belgium"}';
Proctor Notes
  • The partial index lab generates ~15M rows — the INSERT takes a minute or two. Warn attendees.
  • Emphasize the practical use case for partial indexes: active/inactive flags, status columns, soft deletes.
  • For JSONB: the key insight is -> returns JSON, ->> returns text. This matters for WHERE clauses (text comparison vs. JSON containment).
  • GIN indexes are essential for JSONB queries to be fast. Without GIN, @> does a full table scan.
  • The beer products dataset is fun — play with it!

FROM customers WHERE email LIKE '%jones%';

-- Fuzzy matching
SELECT customer_id, first_name, last_name, similarity(last_name, 'Smith') AS sim
FROM customers WHERE last_name % 'Smith'
ORDER BY sim DESC LIMIT 10;

pgcrypto — Password Hashing

CREATE EXTENSION IF NOT EXISTS pgcrypto;
SELECT crypt('my_password', gen_salt('bf', 10)) AS hashed;

-- Verify password
SELECT (crypt('my_password', hashed) = hashed) AS password_matches
FROM (SELECT crypt('my_password', gen_salt('bf', 10)) AS hashed) sub;

pg_cron — Scheduled Jobs

CREATE EXTENSION IF NOT EXISTS pg_cron;
SELECT cron.schedule('nightly-vacuum', '0 3 * * *', 'VACUUM ANALYZE orders');
SELECT cron.schedule('weekly-stats-reset', '0 0 * * 0', 'SELECT pg_stat_reset()');
SELECT * FROM cron.job;
SELECT cron.unschedule('nightly-vacuum');

Requires shared_preload_libraries = pg_cron and cron.database_name = orders_demo in server parameters (restart needed).

27. Cleanup

Learning Objectives
  • Delete all workshop resources to avoid ongoing charges
  • Verify deletion completed
⏱ Timing: 5–10 minutes

CLI Cleanup

# List everything in the resource group
az resource list --resource-group PG-Workshop --output table

# Delete the entire resource group (non-blocking)
az group delete --name PG-Workshop --yes --no-wait

# Verify deletion (may take a few minutes)
az group show --name PG-Workshop

Portal Cleanup (alternative)

  1. Go to Resource groups → PG-Workshop
  2. Click Delete resource group
  3. Type PG-Workshop in confirmation → Delete

Local Cleanup (optional)

rm -f ~/.pg_azure ~/.pgpass
Proctor Notes
  • This is critical. Walk the room and verify every attendee has started the deletion. Leftover resources = unexpected Azure bills.
  • If an attendee created a replica server (logical replication section), remind them to delete that too — it's in the same resource group.
  • If the resource group has a Delete lock (from the managing DB section), it must be removed first: Locks → select lock → Delete.
  • Resource group deletion takes 5–15 minutes. The --no-wait flag returns immediately.
Common Pitfalls
  • "Cannot delete resource group because of locks": Remove the delete lock from the Locks blade first.
  • Attendee forgot their resource group name: az group list --output table shows all groups.
